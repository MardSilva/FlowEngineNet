# Research findings

This log records evidence reviewed for Flow 0.1 and distinguishes implemented observations from hypotheses. Specification links point to the authoritative publisher. Status matters: the HTML Standard is a WHATWG Living Standard; EPUB 3.3 and WCAG 2.2 are W3C Recommendations; several CSS modules cited below remain drafts.

Review date: 2026-08-18.

| Requirement | Existing standard and evidence | 0.1 implementation finding | Gap or limitation | Flow-specific behavior justified? |
| --- | --- | --- | --- | --- |
| Semantic, navigable output | The [HTML Standard sectioning model](https://html.spec.whatwg.org/multipage/sections.html) defines `article`, `section`, `nav`, and heading elements; the [grouping-content model](https://html.spec.whatwg.org/multipage/grouping-content.html#the-figure-element) defines figures and captions. | Flow nodes map cleanly to native elements. Stable node IDs become HTML `id` values and TOC entries become fragment links. | HTML does not define a Flow object model or deterministic Flow-to-HTML bytes. Footnote presentation also remains renderer policy. | No new markup language is justified. A small, tested adapter mapping is justified. |
| Responsive continuous reading | [Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/) separates device/environment queries from document content. [CSS Values and Units Level 4](https://www.w3.org/TR/css-values-4/) defines font-relative and viewport-relative lengths. | CSS is sufficient to make the standalone HTML responsive; Flow also resolves a renderer-independent small/medium/large profile before HTML generation. | The W3C specifications do not provide a renderer-neutral .NET layout object shared by HTML and future native renderers. Media Queries Level 5 is a Working Draft, not a Recommendation. | A renderer-independent decision layer is useful implementation architecture, not a proposed web standard. |
| Typography and reader control | [CSS Fonts Level 4](https://www.w3.org/TR/css-fonts-4/) covers font selection. [CSS Cascading Level 6](https://www.w3.org/TR/css-cascade-6/) defines user-agent, user, and author origins with importance rules. | Existing CSS can express the resolved HTML typography. The Flow cascade similarly separates defaults, author intent, and reader state. | Flow renderer safety constraints are host policy and do not exactly reproduce CSS origin/`!important` ordering. The document model also needs typed values before any CSS exists. | Typed domain values and host safety constraints are justified internally; a new typography syntax is not. |
| Accessibility baseline | [WCAG 2.2](https://www.w3.org/TR/WCAG22/) provides technology-neutral success criteria; [EPUB Accessibility 1.1](https://www.w3.org/TR/epub-a11y-11/) defines EPUB-specific accessibility and discovery metadata. | Semantic HTML, heading hierarchy validation, alternative text retention, inline language/direction ranges, ruby, reader scaling, margins, themes, and safe link handling provide useful building blocks. | Flow 0.1 has no WCAG audit, assistive-technology matrix, complete accessibility metadata model, landmarks profile, language-subtag registry validation, or script-specific layout testing. | No Flow-specific accessibility standard is justified. Compliance claims are explicitly deferred until tested against existing standards. |
| EPUB packaging and default reading order | [EPUB 3.3](https://www.w3.org/TR/epub-33/) defines the OCF ZIP container, package document, exhaustive manifest, spine default reading order, and XHTML content documents. | The prototype maps `container.xml`, expanded OPF metadata/manifest/spine, exact ordered XHTML, fallback chains, navigation, typed CSS, tables, notes, images, and restricted MathML into `FlowDocument`. | Media-overlay playback, fixed layout, encryption, complete accessibility metadata, font embedding, and broad real-publication interoperability remain absent. | No new publication container is justified by this experiment. Broader EPUB mapping should precede any Flow container proposal. |
| EPUB navigation | EPUB 3.3 defines the [EPUB navigation document](https://www.w3.org/TR/epub-33/#sec-nav) as machine- and human-readable publication navigation. | EPUB 3 TOC navigation and EPUB 2 NCX fallback map to `TableOfContents`, stable anchors, and HTML `nav` links. | Landmarks and page-list semantics are not represented; invalid, ambiguous, or cyclic destinations are diagnostic findings. | A Flow TOC node is useful internally, while the importer continues to honor the existing EPUB navigation vocabulary. |
| Embedded SVG and MathML | [SVG 2](https://www.w3.org/TR/SVG2/) defines vector graphics with linking and animation capabilities; [MathML Core](https://www.w3.org/TR/mathml-core/) defines a browser-oriented mathematical markup subset. | SVG is retained only after deterministic active/external-content sanitization. A restricted typed Presentation MathML tree preserves safe block/inline structure and textual alternatives and renders as escaped native MathML. | Flow does not interpret SVG graphics, Content MathML, arbitrary extensions, `annotation-xml`, animation, or external resources. Sanitization can reduce fidelity, and no browser/assistive-technology math matrix has been completed. | A bounded safe projection is justified at the untrusted EPUB boundary; inventing mathematical meaning or a new notation is not. |
| Stable references across renditions | HTML fragment navigation uses element IDs, while EPUB links XHTML resources and fragments inside the publication container. | Flow preserves typed IDs through semantic, layout, and HTML layers and translates supported EPUB links to Flow anchors. | HTML/EPUB fragments are tied to a particular resource structure; Flow anchors still need explicit mapping when import splits, merges, or cannot represent an inline target. EPUB CFI is not implemented or evaluated deeply enough for replacement claims. | A typed internal anchor is justified as an engine invariant; a new public addressing standard is not yet justified. |
| Deterministic semantic hashing | [RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785.html) defines deterministic JSON encoding. | `flow-c14n-0.1` produces stable bytes and explicitly selects canonical semantic fields while excluding presentation and reader state. | JCS does not decide which Flow fields are canonical. The current profile uses fixed schema order rather than JCS lexicographic sorting. | A versioned Flow field projection is justified; a custom final JSON normalization algorithm might not be. Evaluate JCS for a successor profile. |
| Local digital signatures | Standard .NET RSA APIs implement SHA-256 and RSASSA-PSS. | Canonical bytes can be signed and verified without a new algorithm. | Key identity, certificates, distribution, revocation, signature transport, and trust policy are absent. | No Flow-specific cryptography or PKI is justified. |
| Pagination and print | [CSS Paged Media Level 3](https://www.w3.org/TR/css-page-3/) describes page boxes, margins, size, orientation, counters, and fragmentation controls. | Flow 0.1 deliberately exposes no production pagination. `Paged` and `Print` fail explicitly. | The cited module is a Working Draft, implementations vary, and no Flow pagination conformance evidence exists. | No Flow pagination model is justified until existing CSS/renderer behavior is measured in 0.2 experiments. |

## Conclusion for 0.1

The evidence does not support inventing a new general document format. HTML and CSS already cover semantic adaptive presentation well, while EPUB already supplies a standardized portable publication container, metadata, navigation, resources, and reading order. The parts that remain useful in Flow are currently engine-level concerns: an immutable semantic projection, typed stable IDs, explicit canonical-field selection, deterministic research vectors, a renderer-neutral layout boundary, and reader-policy resolution.

The strongest next experiment is not a new container. It is importing a broader, accessibility-aware EPUB corpus into the existing semantic model, measuring every diagnostic and loss, then rendering the result through the same HTML path.
